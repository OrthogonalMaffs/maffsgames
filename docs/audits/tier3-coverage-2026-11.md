# Tier 3 coverage, November 2026 (TIER3-COVERAGE-REPORT)

Home lane, 24 Nov 2026, on origin/main 00ab3245, whose game pages are the same as 77b6a78. Contract: `docs/handover/contracts/2026-11-24-tier3-coverage-report.md`. This is a report only. No checker, allowlist, shared asset or game was changed.

## Summary

Tier 3 visits **116 game pages, in 352 runs**: each game's bare page plus one run for each `?level=` in the roster. It plays **10 of them fully**. Every run of 4 more passes at some levels and not at others. **49 runs pass** and 556 questions are played. The other **303 runs (86%) are UNSUPPORTED**, and UNSUPPORTED never fails the Gate. **No run FAILs.**

- **The lock explains a large part of the gap, but not all of it.**
  - Waiting each tap out takes the runs that pass from 49 to 167 of 352. Questions played rise from 556 to 1597.
  - It takes the games that play fully from 10 to 49.
  - The other 54 unrecorded games are not explained by the lock:
    - 25 never show the driver an option group, so no tap is made at all.
    - 29 still are not marked after a tap that waited out the window. That is a different shape the driver cannot answer.
- **Control.** The same 43 games were run again with the stock driver and no waits, but with `MaffsLock.FRESH_MS` set to 0 by an init script. They behave exactly as with the wait: 39 play fully and 4 play at some levels; 132 of 137 runs pass, against 129 with the wait. So the 300 ms fresh window itself is what stops them, not timing in general.
- **The cloud lane's report is confirmed** for formula-unlocked and scale-factor-scaling.
  - Stock tier 3: all 4 runs of each are UNSUPPORTED with "drove 1 question(s), then question 2 was never marked by a click, a submit or a typed answer; page has no input it knows".
  - Waited out: all 4 runs of each play 10 questions and PASS.
- **Mechanism, from the code.**
  - The driver's first tap comes after the start screen's 700 ms waits, so it lands outside the window and question 1 is marked.
  - Then `next_ready()` (scripts/check-site.py, the stage-2 settle) returns the moment the next question's options differ from the last. The loop taps option 0 at once, within the 250 ms poll step.
  - answer-lock.js's capture guard drops every click for 300 ms after `fresh()` (FRESH_MS, answer-lock.js:74), including the driver's synthetic `.click()`. So question 2 is never marked, and `undrivable()` records UNSUPPORTED.
  - Tier 3 never reads `MaffsLock.isFresh()`. check-answer-lock.py does.

## Method

1. **Stock run.** Tier 3 was run locally exactly as CI does: `python scripts/check-site.py --tier 3 --workers 4 --shard i/4` for i = 1..4, with the default timeout 20000, 10 questions, advance-ms 6000 and seeded Math.random.
   - A throwaway wrapper under `~/t3tool` in WSL, never committed, imports check-site.py and calls its own `tier3()` with those arguments, to keep every run's full result.
   - Each shard took 247 to 457 s: 22.6 min in all at --workers 4.
2. **Comparison with CI.** The local run matches CI on main 77b6a78 (check-site run 45255198196, tier 3 jobs 137978570219 / 137978570268 / 137978570188 / 137978570162) exactly:

| Shard | CI: PASS / UNSUPPORTED / runs, questions | Local: PASS / UNSUPPORTED / runs, questions |
|---|---|---|
| 1/4 | 11 / 74 / 85, 116 | 11 / 74 / 85, 116 |
| 2/4 | 4 / 81 / 85, 89 | 4 / 81 / 85, 89 |
| 3/4 | 9 / 78 / 87, 86 | 9 / 78 / 87, 86 |
| 4/4 | 25 / 70 / 95, 265 | 25 / 70 / 95, 265 |

CI's UNSUPPORTED list and the local one name the same 106 games. Each shard's count of unrecorded games is also the same: 23, 26, 26 and 22, which sum to 97.

3. **Waited out.** The 97 unrecorded games were run again, all levels (285 runs), with the same wrapper. One init script was added after the driver's own. It makes each answer tap (`__mfgClickOpt`, `__mfgClickSubmit`, `__mfgTypeAnswer`) first wait until `MaffsLock.isFresh()` is false, as scripts/check-answer-lock.py does, or 350 ms on a page without MaffsLock. Nothing else changed. The run took 1255 s.
4. **Control.** The 43 games that passed at least one run when waited out were run again with no wait, but with MaffsLock's FRESH_MS set to 0 (933 s).
